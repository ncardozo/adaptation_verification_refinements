\section{Case Study: Bellevue - a Verified Graphical Editor}
\label{sec:case-study}

Having presented the way Refinement Types can help in the verification of completeness properties of 
dynamic adaptations and its implementation within a \ac{COP} language, we now turn our attention to 
the application of such verification approach in building a full-fletched \ac{COP} application, the 
\emph{Bellevue} graphical editor.
This application is used to illustrate how to build a complex application with \ac{COP}, the bugs that 
one may encounter due to inconsistent or incomplete interactions between layers, and the absence of 
said bugs when using our approach.


%%
\subsection{Case Study Design}
\label{sec:design}

Bellevue is a graphical editor developed as a case study to demonstrate the use of Refinement Types 
in the verification of consistency and completeness between layer interactions in \ac{COP} programs.
The main features of Bellevue are:

\begin{enumerate}
  \item Drawing basic pre-defined geometric shapes such as rectangles and circles.
  \item Free hand drawing with a brush by clicking and dragging the mouse over the screen
  \item An eraser
  \item Color fill an arbitrary delimited area using a simple flood-fill algorithm
  \item Selection of colors, brush sizes, eraser radius and other settings
\end{enumerate}

The overall structure of the application follows the \emph{Elm} architecture with three core 
components~\cite{ElmLang25}:
\begin{enumerate*}[label=(\arabic*)]
  \item the \textbf{Model}, which represents the current state of the application,
  \item the \textbf{View}, which specifies how the \textbf{Model} is rendered into HTML, and
  \item the \textbf{Update} function, which specifies how the \textbf{Model} should be updated upon receiving a \textbf{Message}.
\end{enumerate*}

The execution flow of the application is determined by the \textbf{Messages} that exchanged between 
the browser and the application. A \textbf{Message} describes an event that occurred within the 
application. For example, the action of clicking a button sends a \textbf{Message} with data that 
describes the action and information associated with the button. The \textbf{Update} function then has 
to determine, for each \textbf{Message} type, how the state should change (if at all), and what 
additional actions should be performed. These actions are modeled as \textbf{Commands}, and they 
describe the side effects that need to be performed by the application. Actions like logging messages, 
making HTTP requests or drawing into an HTML Canvas, are examples of \textbf{Commands}.

This architectural style is chosen for its simplicity. Since the Elm architecture is a purely functional 
approach for implementing web applications, it is easier to integrate with the \emph{Stainless} 
framework, which is intended for functional programs.

\begin{figure}[pos=hptb]
  \centering
  \includegraphics[width=14cm]{figures/BellevueExample}
  \caption{Bellevue}
  \label{fig:bellevue}
\end{figure}

\fref{fig:bellevue} shows a view of the Bellevue editor with its drawing tools and features.
The full implementation of the application is available at our repository: 
\url{https://github.com/slemus9/bellevue}.

For the case study we implement two versions of Bellevue. The first iteration uses the \ac{COP} 
abstractions purely. The second iteration integrates Refinement types to the first iteration, to assure the 
consistency and completeness of interactions between adaptations, fixing the errors that appear.

\subsection{Implementation}

We use the \emph{Tyrian}~\cite{Indigoengine25} front-end framework to implement Bellevue. Tyrian 
provides an abstraction to develop web applications based on the Elm architecture.

The \textbf{Model} of the application is represented by the \scode{DrawingModel} class in 
\fref{lst:bellevue-model}. It contains data about the current selected tool, the styling configuration 
chosen by the user and the state of the mouse interaction, among other things.

\begin{scala}[label=lst:bellevue-model, caption=Bellevue Model]
final case class DrawingModel(
    selectedTool: Tool,
    brushConfig: StyleConfig,
    colorFillConfig: ColorFillConfig,
    eraserConfig: EraserConfig,
    mouseDragging: Option[MouseDragging],
    receivedMessage: Msg
)
\end{scala}

The \scode{Tool} type in \fref{lst:bellevue-tool} represents a drawing tool that can be selected by the 
user, and it is modeled as a simple enumeration.

\begin{scala}[label=lst:bellevue-tool, caption=Bellevue drawing tools]
enum Tool:
  case Brush, ColorFill, Circle, Eraser, Rectangle
\end{scala}

The mouse interaction is represented by the \scode{MouseDragging} class in 
\fref{lst:bellevue-mouse-dragging}. All drawing actions are performed through mouse dragging: the 
user clicks on any point in the canvas, then drags the mouse across it, and finally releases the mouse.
A \scode{MouseDragging} instance holds the starting position at which the mouse was clicked, and the
latest position that was recorded while the mouse was being dragged.

\begin{scala}[label=lst:bellevue-mouse-dragging, caption=Bellevue mouse dragging modelling]
final case class MouseDragging(
    startPosition: Point,
    latestPosition: Point
)
\end{scala}

Finally, \scode{Msg} is a Sum Type of all types of \textbf{Messages} that can be exchanged in the 
application, as follows.

\begin{scala}[label=lst:bellevue-msg]
type Msg = ControlMsg | MouseMsg | Msg.Partial | ToolboxMsg

enum ControlMsg:
  case HtmlElementLoaded(id: String)
  case MapToCanvas(point: Point, toMouseMsg: Point => MouseMsg)
  case NoAction
  case ResizeCanvas

enum MouseMsg:
  case MouseDown(point: Point)
  case MouseMove(point: Point)
  case MouseUp(point: Point)

enum ToolboxMsg:
  case PickBrushSize(size: Pixels)
  case PickColor(color: RGB)
  case PickEraserRadius(radius: Pixels)
  case PickFillColor(color: RGB)
  case PickTool(tool: Tool)
  case SetCanvasImage(image: Image)
\end{scala}

The logic of the application is defined within the \textbf{Update} function with signature

\begin{scala}[numbers=none, label=lst:bellevue-update-signature]
  def update(model: DrawingModel): Msg => (DrawingModel, Cmd)
\end{scala}

Given a current \scode{model} and a \textbf{Message} of type \scode{Msg}, the \scode{update} 
function returns a new \scode{DrawingModel} together with a \textbf{Command} (side effect) of type 
\scode{Cmd}, that may or may not produce a new \textbf{Message}. Instead of explicitly dispatching 
all types of messages in a single pattern matching block, the \textbf{Update} function is implemented 
as the composition of several \textbf{Predicated Functions}, each of them describing a particular 
drawing interaction, that is implicitly activated as specified by their \scode{isActive} predicate.

For instance, \fref{lst:bellevue-brush-action} shows the definition of \scode{BrushAction}, a 
\textbf{Predicated Function} that draws into the canvas whenever the user wants to perform
a free-hand drawing using the brush.

\begin{scala}[label=lst:bellevue-brush-action, caption=Free hand brush drawing action]
object BrushAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Brush &&
      state.receivedMessage.isInstanceOf[MouseMsg] &&
      state.mouseDragging.isDefined

  override val run: Behavior[DrawingModel, Cmd] = prevAction => model =>
    (model.receivedMessage, model.mouseDragging) match
      case (MouseMsg.MouseMove(to), Some(dragging)) =>
        val from = dragging.latestPosition
        val drawSegment = canvas.drawLineSegment(from, to)
        (model, prevAction |+| drawSegment)

      case (MouseMsg.MouseUp(to), Some(dragging)) =>
        val from = dragging.latestPosition
        val drawSegment = canvas.drawLineSegment(from, to)
        (model, prevAction |+| drawSegment)
\end{scala}

Only when the selected tool is a \scode{Brush} and the user is performing a mouse drag (the 
\scode{isActive} condition), will the \scode{BrushAction} draw a small line segment between the initial 
recorded position and the end position the mouse was dragged to. Note that the \scode{drawSegment} 
side effect is concatenated to the previous action's side effect using the \scode{|+|} operator. This 
means that the action of drawing a line segment will be executed alongside with any other active action.

For the drawing to be consistent, the model needs to be updated so that the \scode{mouseDragging} 
object accurately reflects the user's actions. A separate Predicated Function can be defined just for this 
purpose, as shown in \fref{lst:bellevue-mouse-drag-update-action}.

\begin{scala}[label=lst:bellevue-mouse-drag-update-action, caption=Action to update the mouse dragging state]
object MouseDragUpdateAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.receivedMessage.isInstanceOf[MouseMsg]

  override val run: Behavior[DrawingModel, Cmd] = prevAction => model =>
    model.receivedMessage match
      case MouseMsg.MouseDown(from) => (model.clickMouse(from), prevAction)
      case MouseMsg.MouseMove(to)   => (model.moveMouse(to), prevAction)
      case MouseMsg.MouseUp(_)      => (model.releaseMouse, prevAction)
\end{scala}

The \scode{MouseDragUpdateAction} updates the \scode{mouseDragging} state whenever a 
\scode{MouseMsg} is received. Note that this action does not perform any side effects on its own, as 
it only returns the previous active action's side effect. The only thing it does, is update the model in 
accordance to the received mouse positions. If the user clicks the mouse (\scode{MouseDown}), it 
creates a new \scode{MouseDragging} instance using the mouse position as the 
\scode{startPosition}. If the user is moving the mouse around (\scode{MouseMove}), then it will set the 
\scode{latestPosition} of the \scode{mouseDragging} state to the current mouse position. Otherwise, if 
the user releases the mouse (\scode{MouseUp}), it will set the \scode{mouseDragging} state to 
\scode{None}, signaling that the mouse drag interaction ended.

\begin{scala}[label=lst:bellevue-mouse-drag-update-action-aux, caption=Complementary functions to update the mouse dragging state]
  def clickMouse(startPosition: Point) =
    copy(mouseDragging = Some(MouseDragging.init(startPosition)))

  def moveMouse(to: Point) =
    this.focus(_.mouseDragging.some.latestPosition).replace(to)

  def releaseMouse =
    copy(mouseDragging = None)
\end{scala}

Since most drawing actions are mouse dragging interactions, we abstract the behavior into a separate 
function to enable better reusability, \scode{MouseDragUpdateAction}. Actions like drawing rectangles 
or erasing are similar to the \scode{BrushAction} function, and they also rely on a proper model update 
of the \scode{mouseDragging} state. \fref{lst:bellevue-common-draw-actions-predicates} shows the 
activation predicates for other common drawing actions.

\begin{scala}[label=lst:bellevue-common-draw-actions-predicates, caption=Common drawing actions predicates]
// Draws rectangles
object RectangleAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Rectangle &&
      state.receivedMessage.isInstanceOf[MouseMsg]

// Draws circles
object CircleAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Circle &&
      state.receivedMessage.isInstanceOf[MouseMsg]

// Erases drawings by painting circles of the same color as the background
object EraserCanvasAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Eraser &&
      state.mouseDragging.isDefined &&
      state.receivedMessage.isInstanceOf[MouseMsg]
\end{scala}

Each function defines how to manipulate the canvas independently, starting from a consistent 
\scode{mouseDragging} state. To make sure this is the case, the functions can be composed with the 
\scode{MouseDragUpdateAction} as shown in \fref{lst:bellevue-draw-actions-composition}.

\begin{scala}[label=lst:bellevue-draw-actions-composition, caption=Drawing actions composition]
val DrawAction: PredicatedFunction[DrawingModel, Cmd] =
  PredicatedFunction.sequence(
    PredicatedFunction.oneOf(
      BrushAction,
      CircleAction,
      EraserAction,
      RectangleAction
    ),
    MouseDragUpdateAction
  )
\end{scala}

The implementation of the remaining Bellevue features follow the same structure. The canvas and 
state manipulation are separated into different Ppredicated functions, to be later composed in the 
proper order. Finally, there is a single \scode{BellevueAction} function that comprises all functionality, 
and is used to define the body of the \textbf{Update} function.

\begin{scala}[label=lst:bellevue-update-function-def, caption=Bellevue Update function definition]
val BellevueAction: PredicatedFunction[DrawingModel, Cmd] =
  PredicatedFunction.oneOf(DrawAction, ...)

def update(model: DrawingModel): Msg => (DrawingModel, Cmd) =
  msg => BellevueAction.runWith(model.withMessage(msg), Cmd.None)
\end{scala}

\subsection{Verification with Refinement Types}
\label{sec:verification}

A total of 15 Predicated Functions are defined to specify the \textbf{Update} function. All of them should 
be composed in the right order, taking into account the implicit dependencies between their activation 
conditions. 

During the first iteration of Bellevue, we identified bugs arising from inconsistencies in the interaction 
between the partial functions. There are two types of errors identified in the application, inconsistencies, 
and incomplete behavior.

The first type of error is the incorrectly-ordered compositions, leading to the inconsistent rendering of 
drawings. For instance, if the \scode{MouseDragUpdateAction} is placed as the first function of the 
composition in \fref{lst:bellevue-draw-actions-composition}, some of the drawings will be inconsistent 
with respect to the user actions. This is because, if a \scode{MouseUp} message is received, the 
\scode{releaseMouse} state modification sets the \scode{mouseDragging} value to \scode{None}, even 
when the other functions still need it to perform some operations in the canvas. For example, circles 
would not be drawn at all, since the \scode{MouseUp} event marks the point where the user wants to 
display the final shape.

\begin{scala}[label=lst:enforcing-dependencies, caption=Enforcing dependencies between two predicated functions using Chainable]
final class BrushAction extends PredicatedFunction[DrawingModel, Cmd]:
  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Brush &&
      state.receivedMessage.isInstanceOf[MouseMsg] &&
      state.mouseDragging.isDefined
  ...

final class MouseDragUpdateAction extends PredicatedFunction[DrawingModel, Cmd]:
  override def isActive(state: DrawingModel): Boolean =
    state.receivedMessage.isInstanceOf[MouseMsg]
  ...

// Compiles successfully:
val validChain = new Chainable[DrawingModel, Cmd]:
  override def first = new BrushAction
  override def second = new MouseDragUpdateAction

// Stainless produces compilation error:
val invalidChain = new Chainable[DrawingModel, Cmd]:
  override def first = new MouseDragUpdateAction
  override def second = new BrushAction
\end{scala}

To prevent this type of errors, we can rely on the \scode{Chainable} type (presented in 
\fref{sec:refined-predicated-functions}) to verify that the activation and state manipulation of one 
function, does not deactivate a subsequent function in the composition. The \scode{validChain} value 
compiles successfully in \fref{lst:enforcing-dependencies}, given that the following typing judgement is 
valid.

\begin{equation}
\label{eq:brush-acction-dependency}
\begin{split}
isChainable &: (previous: Cmd) \\
            &\rightarrow (state: DrawingModel) \\
            &\rightarrow unit\{BrushAction.isActive(state) \\
            &\Rightarrow MouseDragUpdateAction.isActive(BrushAction.run(previous, state).first)
\end{split}
\end{equation}

Recall from \fref{lst:bellevue-brush-action} that \scode{BrushAction} returns the previous state without 
modifications in all of its branches, thus \scode{BrushAction.run(previous, state).first = state}, reducing 
the type definition to

\begin{equation*}
\begin{split}
isChainable &: (previous: Cmd) \\
            &\rightarrow (state: DrawingModel) \\
            &\rightarrow unit\{BrushAction.isActive(state) \\
            &\Rightarrow MouseDragUpdateAction.isActive(state)
\end{split}
\end{equation*}

Where the inner implication \scode{BrushAction.isActive(state)} $\Rightarrow$ \scode{MouseDragUpdateAction.isActive(state)} further reduces to

\begin{equation}
\label{eq:brush-mouse-drag-impl}
\begin{split}
(selectedTool = Brush & \; \wedge \; receivedMessage \; : \; MouseMsg \\
  & \; \wedge \; isDefined(mouseDragging)) \\
  & \Rightarrow receivedMessage \; : \; MouseMsg
\end{split}
\end{equation}

The \ac{SMT} solver accepts the implication from Equation \ref{eq:brush-mouse-drag-impl} as a valid 
formula due to the fact that, for any propositions $A$ and $B$, the formula $A \wedge B \Rightarrow B$ 
(and $A \wedge B \Rightarrow A$) is a tautology. On the contrary, \scode{invalidChain} does not 
compile because an implication in the opposite direction does not hold. These values are static checks 
showing that \scode{BrushAction} must necessarily go before \scode{MouseDragUpdateAction} in the 
composition chain, preventing the programmer from composing the predicated functions incorrectly.

This approach can be repeated for all function interactions that need to be verified. Recall from 
\fref{lst:bellevue-draw-actions-composition}, that \scode{BrushAction} is not the only function that must 
go before \scode{MouseDragUpdateAction}. \scode{BrushAction} is accompanied by more alternative 
functions inside the \scode{oneOf} composition, and thus, the dependency relation in 
\fref{eq:brush-acction-dependency} must be guaranteed for all of the other functions as well. 
To achieve this, programmers can define an auxiliary property that verifies that the implication is 
satisfiable for a list of predicated functions, as illustrated in 
\lnrange{ln:list-dependencies-init}{ln:list-dependencies-end} of 
\fref{lst:enforcing-multiple-dependencies}.

\begin{scala}[label=lst:enforcing-multiple-dependencies, caption=Enforcing dependencies between multiple Predicated Functions]
def oneOfLaw(previous: Cmd, state: DrawingModel): Boolean =
  val drawActions  =  List(
    new BrushAction,
    new CircleAction,
    new ColorFillAction,
    new RectangleAction
  )
  val mouseDragUpdate = new MouseDragUpdateAction ` \label{ln:list-dependencies-init} `

  drawActions.forall { action => 
    action.isActive(state) ==> {
      val (newState, _) = action.run(previous, state)
      mouseDragUpdate.isActive(newState)
    }
  }.holds  ` \label{ln:list-dependencies-end} `
\end{scala}

The second type of errors that appear in the implementation of dependencies between partial functions 
comes from the over-specifying the activation predicates. For instance, it makes sense to add the 
\scode{state.mouseDragging.isDefined} condition to the \scode{isActive} predicate of 
\scode{RectangleAction}, just as it was done in the \scode{BrushAction}'s activation predicate.
However, the \scode{RectangleAction} also needs to display an overlaid element to highlight the place 
where the rectangle will be drawn in the canvas; this is done when \scode{state.mouseDragging} is 
equal to \scode{None} (as soon as the new mouse dragging interaction starts). Hence, adding the new 
condition will make the last condition to be silently ignored, as there is no static guarantee that the 
\scode{run} function definition respects the assumptions from the \scode{isActive} predicate. Such 
implementation would create an incomplete application at run time, leading to an crashing error.

\begin{scala}[label=lst:malformed-rectangle-action, caption=Example bug in RectangleAction]
// Example of an ill-specified predicated function for drawing rectangles
object MalformedRectangleAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Rectangle &&
      state.receivedMessage.isInstanceOf[MouseMsg] &&
      state.mouseDragging.isDefined // <-- adding this condition introduces a bug


  override val run: Behavior[DrawingModel, Cmd] = prev => model =>
    (model.receivedMessage, model.mouseDragging) match
      case (MouseMsg.MouseDown(from), None) =>
        // This piece of code is unreachable `\label{ln:malformed-rectangle-action.unreachable}`
        (model, prev |+| overlaidRectangle.show)

      case (MouseMsg.MouseMove(to), Some(dragging)) =>
        val rectangle = Rectangle(from = dragging.startPosition, to)
        (model, prev |+| overlaidRectangle.draw(rectangle))

      case (MouseMsg.MouseUp(to), Some(dragging)) =>
        val rectangle = Rectangle(from = dragging.startPosition, to)
        val draw = canvas.drawRectangle(rectangle) |+| overlaidRectangle.hide
        (model, prev |+| draw)

      case _ => (model, prev)
\end{scala}

\fref{ln:malformed-rectangle-action.unreachable} of \fref{lst:malformed-rectangle-action} states that the 
piece of code that makes the overlaid rectangle visible is ignored, because the \scode{run} function 
patten matching specifies that it should be done when \scode{state.mouseDragging =   None}, but the 
Behavior of \scode{MalformedRectangleAction} will only be executed when 
\scode{state.mouseDragging} is defined, directly contradicting the assumptions from the \scode{run} 
function.

Most bugs that are caused by inconsistent predicates can be detected by adding the \scode{isActive} 
predicate as a pre-condition to the \scode{run} function. This way, it can be guaranteed that the 
\scode{run} function respects the assumptions from the activation predicate, and Stainless will raise an 
error if there are inconsistencies. In this case, we could bring the \scode{isActive} assumptions to the 
\scode{run} function, and then formulate a property asserting that the overlaid rectangle should always 
be visible when a mouse dragging interaction starts. \fref{ln:refined-rectangle-action.property} of 
\fref{lst:refined-rectangle-action} shows a property asserting that for all \scode{prev: Cmd} and 
\scode{model: DrawingModel} values, the \scode{RefinedRectangleAction} should display the overlaid 
rectangle whenever there is a mouse-down interaction, and the \scode{mouseDragging} state is set to 
\scode{None}. This will detect the unreachable code bug encountered previously, because there is no 
possibility that the \scode{overlaidRectangle.isVisible} variable will be set to true, due to the additional 
\scode{state.mouseDragging.isDefined} precondition.

\begin{scala}[label=lst:refined-rectangle-action, caption=Enforcing activation assumptions in the RectagleAction]
final class RefinedRectangleAction extends PredicatedFunction[DrawingModel, Cmd]:

  override def isActive(state: DrawingModel): Boolean =
    state.selectedTool == Tool.Rectangle &&
      state.receivedMessage.isInstanceOf[MouseMsg] &&
      state.mouseDragging.isDefined // <-- adding this condition introduces a bug

  override def run(prev: Cmd, model: DrawingModel): Cmd =
    require(this.isActive(model)) // <-- add precondition
    ...

// This property will fail because the precondition is not met
def overlaidRectVisibleWhenMouseDragging(  ` \label{ln:refined-rectangle-action.property} `
    prev: Cmd,
    model: DrawingModel
    mouseDown: MouseMsg.MouseDown
): Boolean =
  val action = new RefinedRectangleAction
  val inputModel  = model.copy(
    selectedTool = Tool.Rectangle,
    receivedMessage = Msg.Mouse(mouseDown),
    mouseDragging = None()
  )
  // The following call violates the activation precondition:
  val (_, result) = action.run(prev, inputModel)
  result.overlaidRectangle.isVisible
\end{scala}

Though these bugs may seem simple and easy to avoid, they can be hard to detect due to the high 
decoupling between activation and behavior. As the application's complexity increases and new 
predicated functions are defined, the difficulty of finding these simple bugs increases, since there may 
be more interactions that need to be taken into account.

\subsection{Discussion}
\label{sec:discussion}

We evidenced various challenges throughout the development of the first iteration of the Bellevue case 
study. The encountered challenges were mitigated in a second iteration of the application using 
Refinement Types, evidencing its use to verify \ac{COP} programs, and in particular identifying 
inconsistent or incomplete behavior in the application execution caused by the interaction between 
adaptations and their activation rules. Some of the main findings encountered while designing and 
implementing this approach are:

\begin{itemize}
  \item
    Refinement Types are a convenient verification tool because they are integrated with the language 
    in which the application is being implemented, allowing the programmer to verify the actual code 
    that is going to be executed.
    Nonetheless, there are limitations in integrating a code base with the Refinement Types libraries. 
    Though Stainless offers an \scode{@extern} annotation to incorporate Refinements into a program, 
    some Scala compiler errors arise during type checking.
    For instance, it is not possible to use the Tyrian framework's \scode{Cmd[F, A]} type inside the 
    signature of the \scode{PredicatedFunction}.

  \item
    Due to the difficulty of integrating with existing code, a separate notion of \textbf{Commands} had to 
    be implemented in the Stainless \emph{Pure Scala} language subset, which then had to be 
    translated to the Tyrian framework's \scode{Cmd[F, A]} type. This translation process introduces an 
    additional layer of code in the application that is not verified, so further testing or verification is 
    required for this code.

  \item
    Refinement Types are successfully used to verify interactions between predicated functions in this 
    case study. Though the defined properties and dependency relations are specific to the needs of this 
    particular application, there is enough evidence to assert that Refinement Types (and Stainless) is a 
    sufficiently robust tool to reason about inconsistencies or incompleteness in \ac{COP} programs in 
    general.

  \item
    The design choices to implement \scode{PredicatedFunctions} and the Bellevue application 
    facilitated the process of formal verification. The \scode{PredicatedFunction} composition naturally 
    fits into the Elm architecture, since the signature of the \textbf{Update} function is very similar to the 
    definition of a \scode{PredicatedFunction}. The Elm architecture, in turn, made it easier to apply 
    Refinement Types, as we take on a purely functional approach of implementing the application, 
    which is a well suited paradigm for Stainless.

  \item
    The \scode{Chainable} abstraction is sufficient to verify dependencies between predicated functions, 
    however it is not very ergonomic as programmers have to manually construct these instances for all 
    pairs of functions that need to be verified.
    Furthermore, for composition chains longer than two functions, a transitive relation between 
    \scode{Chainable}s must be established for full correctness. A more ergonomic \scode{Chainable} 
    abstraction for multiple functions while enforcing transitivity, is required and left for future work.

  \item
    Another disadvantage of the \scode{Chainable} abstraction, is that is not integrated yet with the 
    \scode{sequence} and \scode{oneOf} composition functions. So, if programmers forget to construct a 
    \scode{Chainable} instance, these composition functions can still be used to potentially construct 
    unsound predicated functions. A more principled approach would be to define \scode{andThen} and 
    \scode{orElse} operations in a way that they receive a \scode{Chainable} instance as an argument, 
    which serves as an \emph{evidence} that two functions can be composed because the given 
    dependency property holds. This way, it is mandatory for the programmer to verify these dependency 
    relations before building compositions.
\end{itemize}


\endinput

\item
    More work can be done to verify more complex properties in this application regarding state transitions. For example, there is a \scode{ColorFill} action that contains the logic of flood-filling a closed area with a selected color.
    This Predicated Function requires the current bitmap of the canvas to be given (i.e. there is a \scode{.canvasImage.isDefined} condition in the activation predicate). It would be desirable to verify that the \scode{ColorFillAction} \emph{always} receives such bitmap when the selected tool is equal to \scode{Tool.ColorFill}.
    The reason why this property is harder to check with the current abstractions, is because the action that sets the bitmap is not directly chained with the \scode{ColorFillAction}, since they happen at two separate time instances.
    A way to tackle this would be to extend the abstractions developed in this work so that the programmer reason about state transitions, and possibly base such implementation in Temporal Logic.
