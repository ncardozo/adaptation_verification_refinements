\section{\ac{COP} in Scala using Predicated Generic Functions}
\label{sec:context-scala}

We now turn our attention to the design and implementation of the proposed predicate-based 
\ac{COP} language in Scala, as well as its integration with Refinement Types using the Stainless 
verifier.


%%
\subsection{Predicated Functions Based on the State Monad}
\label{sec:predicaote-monad}

We present a light-weight \ac{COP} extension for Scala based on predicated generic functions. Our 
implementation has all components required to enable dynamic software adaptations, following the 
scoping and activation rules of \ac{COP} languages. Recall from \fref{sec:cop}, that layers encapsulate 
partial behavior which is in scope only when its associated layer is determined to be active by
the language's activation mechanism. In our implementation, we define layers using the 
\scode{PredicatedFunction} abstraction. A \scode{PredicatedFunction} is the combination of an 
activation condition and a \scode{Behavior}. The activation condition is a predicate that depends on 
the state of the current execution context, while the \scode{Behavior} is a function that may manipulate 
said state and possibly return a result. A \scode{PredicatedFunction} is then a partial function that 
depends on a given state value (\ie context), whose \scode{Behavior} can only be applied if the 
activation predicate evaluates to \scode{true} for for the current state value.

A \scode{Behavior} is represented using the \scode{State} Monad, a function that takes a state and 
returns a product containing the new state and a result, as shown in \fref{lst:state-type}

\begin{scala}[label=lst:state-type, caption=Simplified definition of the State monad]
  type State[S, A] = S => (S, A)
\end{scala}

The \scode{State} type has a \scode{Functor} instance that provides a function to map over the result type, as defined in \fref{lst:state-functor}.

\begin{scala}[label=lst:state-functor, caption=Functor instance for the State type]
 given [S]: Functor[[X] =>> State[S, X]] with

  def map[A, B](fa: State[S, A], f: A => B): State[S, B] =
    state0 =>
      val (state1, a) = fa(state0)
      (state1, f(a))

\end{scala}

Additionally, the \scode{State} type has the \scode{Monad} instance shown in \fref{lst:state-monad}, 
specifying how to chain two state functions sequentially, by threading the initial state through both 
state functions.

\begin{scala}[label=lst:state-monad, caption=Monad instance for the State type]
given [S]: Monad[[X] =>> State[S, X]] with

  def flatMap[A, B](fa: State[S, A], f: A => State[S, B]): State[S, B] =
    state0 =>
      val (state1, a) = fa(state0)
      f(a)(state1)

\end{scala}

In \fref{sec:cop} multiple layers are composed together to form new behavioral variations, in which
each layer within the composition can access the behavior from a previously active layer. To achieve 
the same functionality with \scode{PredicatedFunctions}, we define a \scode{Behavior} to be a 
\scode{State} function that depends on a previously active computation, as illustrated in 
\fref{lst:behavior}.

\begin{scala}[label=lst:behavior, caption=Definition of a \scode{Behavior}]
  type Behavior[S, A] = A => State[S, A]
\end{scala}

Such representation enables a composable definition of partial behavior. \text{Layer} composition is 
translated to function composition, which is easier to implement. Rather than having a special 
\scode{proceed} construct that requires access to meta-level information~\cite{cardozo22},
we use Higher-Order Functions to express state manipulations that may depend on previous 
computations.

Finally, with these definitions in place, a \scode{PredicatedFunction} as a partial \scode{Behavior} 
(\fref{lst:predicated-function}).

\begin{scala}[label=lst:predicated-function, caption=Definition of a \scode{PredicatedFunction}]
 trait PredicatedFunction[S, A]:

  def isActive(state: S): Boolean

  def run: Behavior[S, A]
\end{scala}

We use the \scode{Monad} instance of the \scode{State} type to compose various \scode{Behavior} 
types. There are two strategies to combine two \scode{PredicatedFunctions}. The first strategy, shown 
in \fref{lst:predicated-function-adnThen}, consists on simply running them one after the other and 
feeding the result of the first into the second one. If the \scode{Behavior} of only one of the two 
functions is active according to its predicate for the current state, the corresponding result is returned. 
If both predicated functions are active at the same time, the \scode{Behavior} of both is chained 
together using a \scode{flatMap}. If neither is active, then no \scode{Behavior} is executed, and the 
result of the most recently active \scode{Behavior} is returned.

\begin{scala}[label=lst:predicated-function-andThen, caption=Sequential Composition of Predicated Functions]
infix def andThen[S, A](
    f1: PredicatedFunction[S, A],
    f2: PredicatedFunction[S, A]
) = new PredicatedFunction[S, A]:

  override def isActive(state: S): Boolean =
    f1.isActive(state) || f2.isActive(state)

  override val run: Behavior[S, A] = previous =>
    State.get.flatMap { state =>
      (f1.isActive(state), f2.isActive(state)) match
        case (true, false) => f1.run(previous)
        case (false, true) => f2.run(previous)
        case (true, true)  => f1.run(previous).flatMap(f2.run)
        case _             => passthrough(previous)
    }
\end{scala}

The following auxiliary functions \scode{PassThrough} and \scode{State.get} 
(\fref{lst:predicated-function-andThen-aux}) are used to define the composition function in 
\fref{lst:predicated-function-andThen}.

\begin{scala}[label=lst:predicated-function-andThen-aux, caption=Auxiliary functions to implement Predicated Functions]
/**
* A state transition that does not modify the state, and returns the result of the previous computation
*/
def passthrough[S, A]: Behavior[S, A] =
  previous => state => (state, previous)

object State:
  // Get the current state
  def get[S]: State[S] = state => (state, state)
\end{scala}

The second strategy to compose predicated functions is shown in \fref{lst:predicated-function-orElse}. 
This strategy creates a new function that chooses the first active behavior between the two composed 
functions. Instead of chaining both functions, only one \scode{Behavior} is chosen and executed.

\begin{scala}[label=lst:predicated-function-orElse, caption=Alternating between Predicated Functions]
infix def orElse[S, A](f1: PredicatedFunction[S, A], f2: PredicatedFunction[S, A]) = new PredicatedFunction[S, A]:

  override def isActive(state: S): Boolean =
  f1.isActive(state) || f2.isActive(state)

  override val run: Behavior[S, A] = previous =>
  State.get.flatMap { state =>
    (f1.isActive(state), f2.isActive(state)) match
      case (true, _)     => f1.run(previous)
      case (false, true) => f2.run(previous)
      case _             => passthrough(previous)
  }
\end{scala}

Using either of the strategies as binary operations (\eg \fref{ln:andthen-line}), developers can create 
functions to compose a sequence of predicated functions as shown in 
\fref{lst:predicated-function-compose-multiple}.

\begin{scala}[label=lst:predicated-function-compose-multiple, caption=Composing multiple predicated functions]
object PredicatedFunction:

  def sequence[S, A](
      functions: NonEmptyList[PredicatedFunction[S, A]]
  ): PredicatedFunction[S, A] =
    functions.reduceLeft(_ andThen _) `\label{ln:andthen-line} `

  def oneOf[S, A](
      functions: NonEmptyList[PredicatedFunction[S, A]]
  ): PredicatedFunction[S, A] =
    functions.reduceLeft(_ orElse _)
\end{scala}

Finally, predicated functions can be created by extending the \scode{PredicatedFunction} trait as
shown in \fref{lst:predicated-function-creation-example}. This example shows three 
\scode{PredicatedFunction} that depend on a context state of type \scode{Int}, and return a result of 
type \scode{String}. Each function defines a \scode{Behavior} that may manipulate the state, and 
return a result. For instance, \fref{ln:predicated-function-creation-example.fun2} shows that, when 
\scode{Fun2} is active, it adds 10 to the \scode{state} value, and it appends the 
\scode{"Hello from Fun2."} string to the result of the most recently active \scode{PredicatedFunction}.

\begin{scala}[label=lst:predicated-function-creation-example, caption=Predicated Function examples]
object Fun1 extends PredicatedFunction[Int, String]:
  override def isActive(state: Int): Boolean =
    state < 0

  override def run: Behavior[Int, String] = previous => state =>
    (state, "Hello from Fun1. ")

object Fun2 extends PredicatedFunction[Int, String]:
  override def isActive(state: Int): Boolean =
    state > 0

  override def run: Behavior[Int, String] = previous => state =>
    (state + 10, previous + "Hello from Fun2. ") ` \label{ln:predicated-function-creation-example.fun2} `

object Fun3 extends PredicatedFunction[Int, String]:
  override def isActive(state: Int): Boolean =
    state > 10

  override def run: Behavior[Int, String] = previous => state =>
    (state - 2, previous + "Hello from Fun3. ")
\end{scala}

\fref{lst:predicated-function-composition-example} demonstrates how to combine the \scode{Behavior} 
defined in \fref{lst:predicated-function-creation-example} with our two composition strategies: using 
\scode{sequence} in \fref{ln:predicated-function-composition-example.fun4}, and \scode{oneOf} in 
\fref{ln:predicated-function-composition-example.fun5}.

\begin{scala}[label=lst:predicated-function-composition-example, caption=Predicated Function composition examples]
val initialState = 1
val initialResult = ""

val Fun4 = PredicatedFunction.sequence(Fun1, Fun2, Fun3) `\label{ln:predicated-function-composition-example.fun4}`
val Fun5 = PredicatedFunction.oneOf(Fun1, Fun2, Fun3) `\label{ln:predicated-function-composition-example.fun5}`

val run1 = Fun4.run(initialState)(initialResult) `\label{ln:predicated-function-composition-example.run1}`
// run1 = (9, "Hello from Fun2. Hello from Fun3. ")
val run2 = Fun5.run(initialState)(initialResult) `\label{ln:predicated-function-composition-example.run2}`
// run2 = (11, "Hello from Fun2. ")
\end{scala}

Given an initial state of 1, the result of the \scode{sequence} composition in 
\fref{ln:predicated-function-composition-example.run1} is 
\scode{(9, "Hello from Fun2. Hello from Fun3. ")} because only \scode{Fun2} and \scode{Fun3} are 
active for that particular value. \scode{Fun2} first adds 10 to the initial state, which then activates the 
Behavior of \scode{Fun3} because its predicate requires that \scode{state > 10}.
The result of the \scode{oneOf} composition (\fref{ln:predicated-function-composition-example.run2}), 
on the other hand, is \scode{(11, "Hello from Fun2. ")} because only the first active function in the 
composition is executed.

Note that it is not possible to get into a situation where a predicated function does not have access to
a \scode{previous} computation. This is because their definition requires the programmer to always
give an initial state and an initial value of the result. In the case where no other \scode{Layer} is 
active, the result will be equal to those initial values. As we show next, this simple 
way of structuring programs matches well with the chosen architecture for adaptive systems.

\subsection{Refined Predicated Functions}
\label{sec:refined-predicated-functions}

The \scode{PredicatedFunction} abstraction is enough to construct \ac{COP} programs, however it still 
has many of the disadvantages exposed in \fref{sec:problem-of-verifying-cop} when reasoning about 
the result of a functional composition. Take for instance the code in
\fref{lst:predicated-function-composition-example}. The value of \scode{run1} would be different if the 
programmer composed the functions in a different order; for example, the composition 
\scode{sequence(Fun1, Fun3, Fun2)} yields \scode{(11, "Hello from Fun2.")} when applied to the pair 
 \scode{(1, "")}. Furthermore, the state manipulation of a function may 
contradict the activation predicate of the next function in the composition chain.
\fref{lst:predicated-function-contradictory-composition} shows an example where the first function 
manipulates the state in such a way that the next function will never be available.

\begin{scala}[label=lst:predicated-function-contradictory-composition, caption=Contradictory composition example]
object Fun2 extends PredicatedFunction[Int, String]:
  override def isActive(state: Int): Boolean =
    state > 0

  override def run: Behavior[Int, String] = previous => state =>
    (state - 2 * state, previous + "Hello from Fun2. ")

object Fun3 extends PredicatedFunction[Int, String]:
  override def isActive(state: Int): Boolean =
    state > 10

  override def run: Behavior[Int, String] = previous => state =>
    (state - 2, previous + "Hello from Fun3. ")

// Fun3 is never active whenever Fun2 is, for all possible values of the input state
val Fun6 = PredicatedFunction.sequence(Fun2, Fun3)
\end{scala}

Whether the state manipulations and composition order are coherent or not, depends on the 
requirements of the program. It is the responsibility of the programmer to enforce and validate that 
these requirements are fulfilled. Though this an ubiquitous problem for any program (irrespective of its 
programming paradigm), \ac{COP} programs pose additional challenges when verifying their behavior 
due to the notion of activation. The programmer can (and should) define tests to validate that the 
results for these compositions make sense from a requirements standpoint. However, as stated
in \fref{sec:problem-of-verifying-cop}, a comprehensive validation of a \ac{COP} program can be 
complex and expensive due to the combinatorial explosion of possible states and layer interactions.

Through the use of Refinement types, we propose a verification approach where
we declare the properties that these interactions must fulfill. 
Such approach reduces the cost of exploring the space of possible combinations, because it relies on automated logical reasoning instead of test case generation.
In order to incorporate them into our predicated functions, we modify the \scode{PredicatedFunction} 
definition to add the activation predicate as a precondition to the \scode{run} function, as show in 
\fref{lst:predicated-function-run-precondition}.

\begin{scala}[label=lst:predicated-function-run-precondition, caption=Refinement of the input state type]
abstract class PredicatedFunction[S, A]:

  def isActive(state: S): Boolean

  def run(previous: A, state: S): (S, A) =
    require(this.isActive(state))
    (??? : (S, A))
\end{scala}

Such change refines the type of the \scode{run} function to:

$$
run : A \rightarrow S\{state: S  \: | \: isActive(state) \rightarrow (S, A)\}
$$

Adding the pre-condition to the \scode{run} function's \scode{state} argument means that it can be 
applied only if the caller provides an evidence that the \scode{isActive} predicate holds for the given 
\scode{state} input. Such specification also allows the programmer to bring the assumptions from the 
\scode{isActive} predicate into scope, so that they can be used when defining the program's logic. 
\fref{lst:predicated-function-run-precondition-example} shows a simple example of how an optional 
value can be safely accessed from within the \scode{run} function's scope, due to the \scode{isActive} 
precondition. The \scode{state} function parameter is refined to \lstinline|Option[BigInt]{v : v.isInstanceOf[Some] && v.get > 10}|, guaranteeing that \scode{state.get} will never throw an exception as it should always be an instance of the \scode{Some} type.

\begin{scala}[label=lst:predicated-function-run-precondition-example, caption=Refinement Typed-Checked example of the run function]
object RefinedFun1 extends PredicatedFunction[Option[BigInt], String]:

  override def isActive(state: Option[BigInt]): Boolean =
    state match
      case Some(x) => x > 10
      case None    => false

  override def run(
      previous: String,
      state: Option[BigInt]
  ): (Option[BigInt], String) =
    // The .get call is safe and verified at compile-time.
    // The isActive precondition states that this function
    // can only be called when the optional value is defined
    (state.get - 9, "Hello from Fun1. ")
\end{scala}

From this simple restriction, more complex properties can be defined between two or more functions 
that interact with each other. It is up to the programmer to define these properties per the program's 
requirements. For example, it is particularly useful to ensure that the activation and execution of a 
predicated function does not deactivate the next function in the composition chain. This can be 
formalized with Refinement Types as a predicate stating that the activation of the first function implies 
the activation of the second one. It is not enough, however, to establish a relation between the 
activation predicates without taking into account the actual logic of the functions. Recall from previous 
examples that each function can manipulate the state, and it may do so in such a way that the next 
function becomes deactivated for certain state values.
A proper formulation should then assert that the activation and state manipulation of the first function, 
implies that the next function will always be active. The \scode{Chainable} abstraction in 
\fref{lst:predicated-function-chainable} formalizes such property.

\begin{scala}[label=lst:predicated-function-chainable, caption=Chainable type for expressing and verifying dependencies between predicated functions]
abstract class Chainable[S, A]:

  def first: PredicatedFunction[S, A]
  def second: PredicatedFunction[S, A]

  @law
  def isChainable(previous: A, state: S): Boolean =
    first.isActive(state) ==> {
      val (newState, _) = first.run(previous, state) ` \label{ln:predicated-function-chainable.first.run} `
      second.isActive(newState)
    }
\end{scala}

An instance of the \scode{Chainable} type serves as an evidence that, for the given \scode{first} and 
\scode{second} predicated functions, the \scode{isChainable} predicate holds for all possible values of 
\scode{previous: A} and \scode{state: S}. This property states that the activation condition of the 
\scode{first} function implies that, when applying it to the previous result and state, the \scode{second} 
function will be active for the new returned state. The type of the \scode{isChainable} property is shown 
in Equation \ref{eqn:isChainable}.

\begin{equation}
\label{eqn:isChainable}
\begin{split}
isChainable &: (previous: A) \\
            &\rightarrow (state: S) \\
            &\rightarrow unit\{f1.isActive(state) \\
            &\Rightarrow f2.isActive(f1.run(previous, state).first)\}
\end{split}
\end{equation}


Note that the \scode{first.run} call on \fref{ln:predicated-function-chainable.first.run} must necessarily 
happen inside the right hand side block of the implication (\scode{==>}) because the \scode{run} 
function's precondition states that the \scode{isActive} predicate should hold for the given state input.

\fref{lst:predicated-function-chainable-example} shows two functions that satisfy this implication for all 
possible state values.

\begin{scala}[label=lst:predicated-function-chainable-example, caption=Chainable type usage example]
final class RefinedFun1 extends PredicatedFunction[Option[BigInt], String]:

  override def isActive(state: Option[BigInt]): Boolean =
    state match
      case Some(x) => x > 10
      case _       => false

  override def run(
      previous: String,
      state: Option[BigInt]
  ): (Option[BigInt], String) =
    (state.get - 9, "Hello from Fun1. ")

final class RefinedFun2 extends PredicatedFunction[Option[BigInt], String]:
  override def isActive(state: Option[BigInt]): Boolean =
    state match
      case Some(x) => x > 1
      case _       => false

  override def run(
      previous: String,
      state: Option[BigInt]
  ): (Option[BigInt], String) =
    (state.get + 1, "Hello from Fun2. ")

// Stainless automatically verifies that the isChainable law holds for the given functions
val chain = new Chainable[Option[BigInt], String]:
  def first: PredicatedFunction[Option[BigInt], String] = new RefinedFun1
  def second: PredicatedFunction[Option[BigInt], String] = new RefinedFun2
\end{scala}

When instantiating a new \scode{Chainable} instance with two concrete predicated functions, Stainless 
will automatically verify that the \scode{isChainable} law holds for those particular functions. If, for 
instance, \scode{RefinedFun1} subtracted 10 instead of 9 to the input state (\scode{state.get - 10}), 
then the programmer would get a compilation error because there exists a \scode{state} value for which 
the \scode{isChainable} property does not hold. The SMT solver will also return an example of a value 
that makes the predicate false (in this case \scode{state =  11}).
